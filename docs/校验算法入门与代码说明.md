# 校验算法入门与代码说明

> 当前专项文档，最后核对：2026-08-01。补充结论：S3 触觉 SPI CRC8 是查表法；S3/P4 批次 CRC16 和 Manual/多圈 NVS CRC32 是逐位移项法；Classic CAN 单帧 CRC 由 TWAI 硬件完成。完整使用位置和选择理由见[通信协议与数据校验](通信协议与数据校验.md)。

这份文档结合当前代码，解释项目里出现的几类“校验”：

- 数据完整性校验：判断一串数据在传输或存储过程中有没有被改坏，例如奇偶校验、CRC8、CRC32。
- 通信帧结构校验：判断一包数据是不是符合协议格式，例如帧头、长度、帧尾、分包序号。
- 业务有效性校验：判断数据虽然能读到，但是否允许用于控制，例如有效标志、断连标志、范围限制、急停条件。

它们不是一回事。CRC 解决的是“这包字节有没有变坏”，范围限制解决的是“这个目标值会不会把舵机打到危险位置”，稳定窗口解决的是“这个物理现象是不是持续发生”。

## 一句话总览

当前代码里的主要校验点如下：

| 位置 | 校验类型 | 作用 |
| --- | --- | --- |
| S3 磁编码器读取 | AS5047P 16 bit 偶校验 + 芯片错误位 | 检查 SPI 读回帧是否坏、芯片是否报告错误 |
| S3 触觉读取 | CRC8 | 检查触觉模块 SPI 返回包是否完整 |
| S3 到 P4 CAN | CAN 硬件 CRC + 软件分包重组 | CAN 控制器负责底层帧 CRC，代码负责多帧数据是否凑齐 |
| P4 到上位机串口 | 帧头、长度、帧尾、payload 长度 | 检查串口帧格式，目前没有 CRC |
| P4 多圈 NVS | CRC32 + magic/version/sequence | 检查掉电保存的多圈数据是否可靠 |
| 控制链路 | validFlags、errorFlags、clamp、active mask | 防止无效传感器、越界目标或错误关节进入控制 |

## 先入门：校验到底在检查什么

### 奇偶校验

奇偶校验是最简单的校验。它只统计一个数据里有多少个 1。

例如 AS5047P 使用 16 bit 帧，其中最高 bit 是 parity bit。代码让整帧满足“偶校验”：整帧里 1 的数量应该是偶数。

优点是简单、开销小。缺点也明显：如果刚好有两个 bit 同时翻转，奇偶校验可能发现不了。

### CRC

CRC 可以理解成对一串字节做一次“除法余数计算”，最后得到一个短结果。发送方把 CRC 附在数据后面，接收方重新算一遍，如果两边结果不一样，就说明数据大概率坏了。

CRC8 结果是 1 字节，CRC32 结果是 4 字节。CRC32 检错能力比 CRC8 强，但开销也更大。

注意：CRC 不是加密，也不能防止别人故意伪造。它主要用于发现误码、丢字节、写坏 flash 等问题。

### 帧结构校验

很多通信包并没有 CRC，但会检查：

- 帧头是不是正确。
- 长度是不是合理。
- 帧尾是不是正确。
- 命令类型是否已知。
- payload 长度是否和命令定义一致。

这类校验能防止串口流错位，但不能像 CRC 那样发现 payload 内部某一个字节被改坏。

### 业务有效性校验

例如：

- 传感器断连，不能用于控制。
- 目标角度超过标定范围，需要 clamp。
- 当前关节没有勾选，就不能发送目标。
- 急停状态下不能继续负反馈输出。

这些不是数学上的 checksum，但对机器人控制更重要。

## 当前数据流里的校验层级

简化数据流如下：

```text
磁编/触觉硬件
  -> S3 SPI 读取和校验
  -> S3 CAN 发送
  -> P4 CAN 接收和重组
  -> P4 控制/标定/状态机
  -> P4 串口协议
  -> 桌面上位机解析和显示
```

多圈保存是另一条链路：

```text
P4 舵机反馈
  -> 生成 NVS snapshot
  -> CRC32 写入 flash
  -> 下次开机读取并校验
```

### 发送命令时怎么生成 parity

代码大致逻辑是：

```cpp
uint16_t HalEncoders::build_command_frame(uint16_t addr, bool is_read) {
    if (is_read) {
        addr |= 0x4000;
    }
    if (get_parity(addr & 0x7FFF)) {
        addr |= 0x8000;
    }
    return addr;
}
```

这里的含义是：

- bit 14 是读写位，读命令会置 `0x4000`。
- bit 15 是 parity 位。
- 先只统计低 15 bit 里 1 的数量。
- 如果低 15 bit 的 1 个数是奇数，就把 bit 15 置 1，让整帧变成偶数个 1。

所以这里做的是偶校验。

### 接收数据时怎么判断错误

`decodeFrame(...)` 里会检查：

```cpp
if (get_parity(rawVal & 0x7FFF) != ((rawVal >> 15) & 0x01)) {
    _latchedErrorCodes[encoderId] = ERR_CODE_ERRFL_BASE | AS5047P_ERR_PARERR;
    _fsmStates[encoderId] = FSM_READ_ERRFL;
    return;
}
```

可以这样理解：

- `rawVal & 0x7FFF` 是去掉最高 parity bit 后的数据。
- `get_parity(...)` 计算低 15 bit 的奇偶性。
- `((rawVal >> 15) & 0x01)` 是芯片返回的 parity bit。
- 两者不匹配，说明这帧数据 parity 不对。

发现 parity 错后，代码不会继续相信这帧角度，而是设置错误码，并进入 `FSM_READ_ERRFL` 去读芯片错误寄存器。

### AS5047P error bit

除了 parity，AS5047P 返回帧里还有一个 error bit：

```cpp
const bool errorBit = (rawVal & 0x4000) != 0;
```

如果 error bit 被置位，说明芯片本身认为刚刚的访问或内部状态有问题。代码会进入 `FSM_READ_ERRFL`，读取 `AS5047P_REG_ERRFL`。

`ERRFL` 里能看到更细的错误，比如：

- parity error
- frame error
- invalid command

如果打开了完整诊断，还会读 `AS5047P_REG_DIAAGC`，用于判断磁场过低、过高等问题。

### 这层校验能防什么

能发现：

- SPI 线上某一位随机翻转。
- 芯片报告命令无效。
- 芯片报告帧错误。
- 磁场异常类诊断。

不能完全发现：

- 两个 bit 同时翻转且刚好抵消 parity。
- 物理安装导致读数方向不对。
- 编码器读数本身稳定但映射表配错。

所以 parity 只能说明“这帧通信大概率没坏”，不能说明“这个关节映射一定正确”。

## 2. 触觉模块 CRC8

相关文件：

- CRC 比较：`ESP32-S3/System/src/hal/HalTactile.cpp:227`
- 读取重试：`ESP32-S3/System/src/hal/HalTactile.cpp:264`

### CRC8 怎么算

当前实现是查表法：

```cpp
uint8_t HalTactile::crc8(const uint8_t* data, uint32_t len) {
    uint8_t crc = 0xFF;
    while (len--) {
        crc = kCrc8Table[crc ^ *data++];
    }
    return crc;
}
```

关键点：

- 初始值是 `0xFF`。
- 每读一个字节，就用当前 crc 和这个字节异或。
- 异或结果作为索引查 `kCrc8Table`。
- 最后得到 1 字节 CRC。

查表法和逐 bit 算法结果一样，只是速度更快。

### 触觉返回包怎么校验

`readRegisters(...)` 会读取触觉模块返回的一整包数据。最后一个字节是触觉模块给出的 CRC：

```cpp
const uint8_t recvCrc = raw[totalLen - 1];
const uint8_t calcCrc = crc8(raw, totalLen - 1);

if (recvCrc != calcCrc) {
    memset(payload, 0, payloadLen);
    ...
    return false;
}
```

也就是：

- `recvCrc`：设备返回包最后一个字节。
- `calcCrc`：S3 自己重新计算前面所有字节的 CRC。
- 两者不同，说明触觉 SPI 返回包有问题。

失败后代码会把 payload 清零，并记录诊断信息：

- `lastRecvCrc`
- `lastCalcCrc`
- `lastFailRecvCrc`
- `lastFailCalcCrc`

### 重试和零保持不是 CRC

触觉读取还有两层逻辑容易和 CRC 混淆：

- `kReadRetryCount = 3`：CRC 错或读取失败时最多重试 3 次。
- `kZeroNoiseFloor = 3`、`kZeroHoldFrames = 6`：触觉值短时间变成 0 时，做一点保持，避免 UI 和控制侧马上跳 0。

这两层是稳定性处理，不是数据完整性校验。

### 这层校验能防什么

能发现：

- 触觉 SPI 返回包中某个字节错误。
- 读包长度正确但内容被干扰。
- 触觉数据和 CRC 对不上。

不能发现：

- 触觉模块自己测量值物理上不准，但返回包 CRC 正确。
- 触觉分组映射错，比如 SPI 组对应手指顺序错。
- CAN 发送阶段之后发生的数据混组问题，这要靠 CAN 分包重组检查。

### 先说明：CAN 硬件本身有 CRC

TWAI/CAN 控制器底层帧自带 CRC、ACK、仲裁等机制。代码里看不到 CAN CRC 的计算，因为这是硬件控制器做的。

代码层主要做的是更高层的“分包是否完整、顺序是否属于同一批”。

### 磁编 CAN 帧

S3 发送磁编数据：

- CAN ID 从 `0x100` 开始。
- 21 个磁编，每 4 路一帧。
- 总共 6 帧，最后一帧只有 1 路有效数据。

S3 发送位置：

- `ESP32-S3/System/src/hal/HalTWAI.cpp:71`
- `ESP32-S3/System/src/hal/HalTWAI.cpp:81`

P4 接收位置：

- `ESP32-P4/ServoBoardMain/src/communication/can/CanCommTask.cpp:174`
- 收到 `CAN_ID_ENC_LAST` 时覆盖 `canRxQueue`：`ESP32-P4/ServoBoardMain/src/communication/can/CanCommTask.cpp:194`

当前磁编帧没有 seq，也没有 frameMask 完整性判断。也就是说：

- 每收到一帧就更新对应通道。
- 收到最后一帧时，认为这一轮可以发布。
- 如果中间某一帧丢了，对应通道可能保留上一轮旧值。

这在 CAN 丢包很少时通常没问题，但从严格校验角度看，磁编分包没有触觉那样完整。

- CAN ID 从 `0x240` 到 `0x246`。
- 总共 7 帧。
- 每帧第 0 字节是 `seq`。
- 后 7 字节是连续触觉 payload 片段。

P4 重组位置：

- `TactileReassemblyState`：`ESP32-P4/ServoBoardMain/src/communication/can/CanCommTask.cpp:82`
- 触觉帧处理：`ESP32-P4/ServoBoardMain/src/communication/can/CanCommTask.cpp:241`

判断逻辑可以理解成：

```text
收到第 1 帧：
  记下 seq，清空 frameMask

后续帧：
  如果 seq 变了，说明不是同一批，旧批丢弃

  说明 7 帧都到了
```

### 帧格式

当前上下行串口帧格式是：

```text
[0xFE][LEN][TYPE 或 CMD][PAYLOAD][0xFF]
```

其中：

- `0xFE` 是帧头。
- `LEN` 是长度字段。
- 中间是 packet type 或 command，加 payload。

- 帧尾是否是 `PROTOCOL_TAIL`。

- payload 长度是否等于该命令规定长度。

### 上位机接收下位机数据

桌面端解析在两个地方有类似逻辑：

- `desktop/core/protocol.py:345`
- `desktop/core/comm_layer.py:473`

`comm_layer.py` 还有一个有用特性：如果收到的字节不是协议帧头，就把它当成固件日志文本缓存并打印。这就是为什么固件里的 `[AUTO CALIB]`、`[RX diag]` 能在终端出现，而协议包仍能被解析。

### 当前串口协议没有 CRC

这一点很重要：当前 P4 到上位机、上位机到 P4 的串口协议没有 CRC8/CRC16/CRC32。

所以它能发现：

- 帧头错。
- 帧尾错。
- 长度错。
- 命令 payload 长度错。

但它不一定能发现：

- payload 中某个字节被干扰，但刚好帧头、长度、帧尾仍然正确。

目前 USB 串口环境下这个风险通常不高，但如果后续出现“偶发目标角度乱跳、协议包看起来合法但内容异常”，可以考虑在帧尾前增加 CRC8 或 CRC16。

建议格式可以是：

```text
[0xFE][LEN][TYPE/CMD][PAYLOAD][CRC][0xFF]
```

这样 P4 和桌面端都要同步升级。

### CRC32 算法

代码位置：

- `crc32Update(...)`：`ESP32-P4/ServoBoardMain/src/persistence/MultiTurnNvsStore.cpp:43`
- `snapshotCrc(...)`：`ESP32-P4/ServoBoardMain/src/persistence/MultiTurnNvsStore.cpp:56`

当前 CRC32 使用多项式：

```cpp
0xEDB88320UL
```

这是常见的 reflected CRC32 多项式。计算时：

- 初始会取反。
- 每个字节参与异或。
- 每个字节循环 8 个 bit。
- 最后再取反。

### 为什么 CRC 不包含 crc32 自己

`snapshotCrc(...)` 用了：

```cpp
offsetof(MultiTurnNvsSnapshot, crc32)
```

意思是只计算从结构体开头到 `crc32` 字段之前的内容。这样做很合理，因为如果把 `crc32` 自己也参与计算，会变成“用结果校验结果”，逻辑上很难稳定。

### 读取时怎么判断 snapshot 可信

`validateSnapshot(...)` 检查：

- `magic` 是否等于 `MTN1`。
- `version` 是否匹配。
- `motorCount` 是否等于当前 `SERVO_TOTAL_NUM`。
- `crc32` 是否等于重新计算的 CRC。

位置：

- `ESP32-P4/ServoBoardMain/src/persistence/MultiTurnNvsStore.cpp:61`

如果不通过，`loadSlot(...)` 会把这个 slot 当作不存在：

- `ESP32-P4/ServoBoardMain/src/persistence/MultiTurnNvsStore.cpp:72`
- `ESP32-P4/ServoBoardMain/src/persistence/MultiTurnNvsStore.cpp:84`

## 6. 控制链路里的有效性校验

这些不是 CRC，但直接关系到安全。

### 磁编断连和 validFlags

P4 控制任务把磁编原始值映射成关节角时，会设置 `mappedData.validFlags[i]`。

### 急停判断

- 当前关节是否有 sensor error。

## 7. 标定里的窗口判定也算校验吗

自动标定里有大量类似：

- 角度窗口小于阈值。
- 连续几个窗口稳定。
- 负载超过阈值。
- 是否曾经经过 0 度附近。
- 松绳方向是否反向。
- wrongStable / reverseStable。

这些更准确地说是“物理状态判定”，不是通信校验算法。

它们的作用是判断：

- 是否顶到机械端点。
- 是否已经回拉到预期位置。
- 是否发生了危险的反向收绳。
- 是否因为噪声导致误判。

它们和 CRC 的区别是：

- CRC 判断字节数据是否损坏。
- 标定窗口判断物理运动是否符合预期。

所以调这类阈值时，不能按 CRC 的思路调，而要看机械负载、编码器窗口、舵机 ABS 运动方向、连续稳定次数。

## 8. 目前代码的薄弱点和可改进方向

### 1. 串口协议可以考虑加 CRC

当前串口协议没有 CRC。如果以后遇到偶发合法帧但 payload 异常，可以加 CRC8 或 CRC16。

改动范围：

- P4 `UpperCommTask.cpp` 发送和接收。
- P4 `UpperCommProtocol.h` 长度定义。
- 桌面端 `desktop/core/protocol.py` 构包和拆包。
- 桌面端 `desktop/core/comm_layer.py` 流式解析。

### 2. 磁编 CAN 分包可以加 seq/frameMask

触觉数据已经有 seq 和 frameMask，磁编数据目前没有。如果 CAN 总线很忙或偶发丢帧，中间帧可能沿用旧值。

更严谨的做法：

- 每轮磁编 6 帧带相同 seq。
- P4 维护 `encoderFrameMask`。
- 收齐 6 帧且 seq 相同才发布 `canRxQueue`。

代价是每帧 payload 会少 1 字节，需要重新设计 21 路编码器的 CAN 打包方式。

### 3. 触觉 CRC 错误计数可以上传到上位机

现在 S3 内部记录了触觉 CRC 诊断，但上位机不一定能直观看到。

可以考虑把：

- 最近一次 `recvCrc`
- 最近一次 `calcCrc`
- CRC fail count
- retry fail count

通过 CAN 或调试串口上传，这样排查触觉线束和 SPI 问题会更直接。

### 4. 把“校验失败”和“物理异常”在 UI 上分开显示

例如：

- 通信校验失败：CRC/parity/CAN reassembly。
- 传感器物理异常：磁场太弱、磁场太强。
- 控制安全异常：越界、急停、反向收绳。

这样调试时不会把“线坏了”和“机械方向错了”混在一起。

## 9. 看日志时怎么判断是哪一层出问题

### 磁编读数星号或角度无效

优先看：

- S3 AS5047P parity / ERRFL / DIAAGC。
- P4 `sensorData.errorFlags`。
- 上位机 Enc 列是否显示错误。

可能是 SPI 线、磁铁距离、磁场强弱、编码器本体或映射方向。

### 触觉 UI 某组不动或跳 0

优先看：

- S3 触觉 CRC 是否失败。
- CAN 触觉 7 帧是否能收齐。
- P4 tactile reassembly 是否因 seq 改变或 80 ms 超时丢包。
- 触觉 SPI 分组映射是否和 UI G0-G4 对应。

如果某组一直显示成另一个手指，优先查映射，不要先怀疑 CRC。

### 上位机偶发 CAN 错误但数据还在刷新

可能不是底层 CAN 完全断，而是某类数据超时或重组不完整。例如触觉分包没收齐，会影响上位机对“整体通信健康”的判断。

这类问题要区分：

- 磁编帧是否还稳定。
- 触觉帧是否还稳定。
- 错误详情帧是否还稳定。
- 上位机判断 CAN offline 的超时时间是多少。

### 多圈上电后没有恢复

优先看：

- Flash 开关是否开启。
- NVS snapshot 是否存在。
- `magic/version/motorCount/crc32` 是否校验通过。
- 桌面端 `multiturn_cache.json` 是否被禁用或清除。

Flash OFF 时你已经要求同时禁用下位机 NVS 和上位机缓存恢复，这会影响恢复行为。

## 10. 小结

当前项目里最重要的校验可以这样记：

- 磁编 SPI：AS5047P parity 和 ERRFL，防 SPI 帧错误和芯片错误。
- 触觉 SPI：CRC8，防触觉模块返回包损坏。
- CAN 触觉和错误详情：seq + frameMask + timeout，防多帧混批和缺帧。
- 串口上下位机：帧头、长度、帧尾、payload 长度，目前没有 CRC。
- 多圈 NVS：CRC32 + A/B slot + sequence，防 flash 掉电写坏。
- 控制安全：validFlags、errorFlags、clamp、active mask，防无效数据和越界目标进入控制。

如果以后要提升抗干扰能力，优先级我建议是：

1. 给上位机串口协议加 CRC8 或 CRC16。
2. 给磁编 CAN 分包加 seq/frameMask。
3. 把触觉 CRC 失败计数和 CAN 重组失败计数显示到上位机。
4. 在 UI 上把通信校验错误、传感器物理错误、控制安全错误分开显示。
