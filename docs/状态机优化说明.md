# 状态机优化说明

本文档记录本轮对 ESP32-P4 固件状态机、通信命令路由、保护故障和自动标定流程做出的优化。目的是让后续开发者明确：现在谁负责切换状态、哪些故障需要 RESET 才能清除、哪些命令只是排队、哪些操作在运行中被禁止。

相关主要文件：

- `ESP32-P4/ServoBoardMain/src/system/StateMachineTask.cpp`
- `ESP32-P4/ServoBoardMain/src/shared/TaskSharedData.h`
- `ESP32-P4/ServoBoardMain/src/communication/upper/UpperCommTask.cpp`
- `ESP32-P4/ServoBoardMain/src/communication/upper/UpperCommCommandRouter.cpp`
- `ESP32-P4/ServoBoardMain/src/calibration/AutoCalibrationTask.cpp`
- `desktop/protocol.py`
- `desktop/comm_layer.py`

## 1. 当前主状态流程

顶层状态机现在保留以下状态：

| 状态 | 含义 |
| --- | --- |
| `SYSTEM_STATE_UNCONTROLLABLE` | 不可控 / 急停 / 故障保持 / 未满足可控条件 |
| `SYSTEM_STATE_IDLE` | 可控但尚未满足关节闭环 READY 条件 |
| `SYSTEM_STATE_READY` | 已满足关节闭环准入条件，可进入 `RUN_FEEDBACK` |
| `SYSTEM_STATE_RUN_DIRECT` | 电机直控运行 |
| `SYSTEM_STATE_RUN_FEEDBACK` | 关节负反馈闭环运行 |
| `SYSTEM_STATE_CALIBRATION_RUNNING` | 固件自动标定运行中 |
| `SYSTEM_STATE_PAUSED` | 暂停输出，保留恢复目标 |

已删除 `SYSTEM_STATE_STOPPED`。现在 `STOP` 语义统一为急停/不可控保持，最终回到 `UNCONTROLLABLE`。

主流程：

```text
UNCONTROLLABLE
  -- START/ENABLE 且反馈、scope、fault 条件满足 -->
IDLE
  -- active joints 在工作空间内且多圈可信 -->
READY
  -- RUN_FEEDBACK -->
RUN_FEEDBACK

IDLE / READY
  -- RUN_DIRECT -->
RUN_DIRECT

RUN_DIRECT / RUN_FEEDBACK
  -- PAUSE -->
PAUSED
  -- START/ENABLE -->
恢复到暂停前的 RUN_DIRECT 或 RUN_FEEDBACK

IDLE / READY
  -- CALIBRATE -->
CALIBRATION_RUNNING
  -- success -->
IDLE 或 READY
  -- failed -->
UNCONTROLLABLE + CALIB fault

任意关键故障或 STOP
  --> UNCONTROLLABLE

RESET
  --> 清除锁存故障并回到 UNCONTROLLABLE
```

## 2. 本轮优化内容

### 2.1 状态机统一裁决 `control_mode`

之前通信路由收到关节角度包会直接写 `CONTROL_MODE_JOINT`，收到电机直控包会直接写 `CONTROL_MODE_DIRECT_MOTOR`。这会导致一种不一致状态：通信层已经改了 `control_mode`，但 StateMachineTask 可能拒绝 `RUN_DIRECT` 或 `RUN_FEEDBACK` 事件。

现在改为：

- `UpperCommCommandRouter` 只写目标值、token 和 direct command source。
- `StateMachineTask` 在真正接受 `SYSTEM_EVENT_RUN_DIRECT` 后才设置 `CONTROL_MODE_DIRECT_MOTOR`。
- `StateMachineTask` 在真正接受 `SYSTEM_EVENT_RUN_FEEDBACK` 后才设置 `CONTROL_MODE_JOINT`。
- 从 `PAUSED` 恢复时也由状态机根据 `paused_resume_state` 重新设置 `control_mode`。

这样保证 `system_state`、`servo_target_owner`、`control_enabled`、`control_mode` 四者一致。

### 2.2 删除 `STOPPED`

`STOPPED` 状态过去只在协议和上位机里有语义，但固件 STOP 分支实际进入的是 `UNCONTROLLABLE`。这容易让 UI、协议、固件三方含义不一致。

现在：

- 固件删除 `SYSTEM_STATE_STOPPED` 定义。
- 上位机删除 `SYSTEM_STATE_STOPPED` 常量。
- `CMD_STOP` 的本地状态推断统一为 `UNCONTROLLABLE`。

### 2.3 保护故障只能通过 RESET 清除

之前 `START`、`RUN_DIRECT`、`RUN_FEEDBACK` 会触发 overload/release fault reset token，导致按 ENABLE 就可能清除保护锁存。

现在：

- `START` 不再清除 overload/release fault。
- `RUN_DIRECT` 不再清除 overload/release fault。
- `RUN_FEEDBACK` 不再清除 overload/release fault。
- 只有 `RESET` 会清除 overload/release fault reset token 和系统 fault latch。

这使保护故障更符合安全语义：过载或反向释放保护触发后，需要明确 RESET 才能恢复。

### 2.4 calibration 也纳入 overload 保护

控制任务中的 overload 已覆盖 `RUN_DIRECT` 和 `RUN_FEEDBACK`，但自动标定走 `SERVO_TARGET_OWNER_CALIBRATION`，不经过正常控制输出分支。

现在在 `AutoCalibrationTask.cpp` 中增加 calibration batch 发布前的 overload 检查：

- 每次发布 calibration batch 前，遍历 batch 内目标电机。
- 读取对应电机 telemetry load。
- 若 `load >= 800`，设置 `overload_fault_bitmap` 对应 bit。
- 当前自动标定失败，状态机随后进入 `UNCONTROLLABLE`，并显示 overload / CALIB fault。

### 2.5 标定失败锁存 CALIB fault

之前 `CALIB FAILED` 时 `calibration_fault_latched` 被清零，导致 UI 可能显示标定失败，但系统 fault 不显示 `CALIB`。

现在：

- `SYSTEM_EVENT_CALIBRATION_FAILED` 分支设置 `calibration_fault_latched = 1`。
- `startAutoCalibrationTask()` 启动失败也设置 `calibration_fault_latched = 1`。
- `collectSystemFaults()` 会把该 latch 映射为 `SYSTEM_FAULT_CALIBRATION`。
- `RESET` 后清除该 latch。

### 2.6 限制 ACTIVE_SCOPE 修改时机

`ACTIVE_SCOPE` 会影响 active motor、active joint、是否要求 CAN feedback，属于安全边界配置。过去通信层可以直接修改。

现在只允许在以下条件全部满足时接受：

- `system_state` 是 `IDLE`、`READY` 或 `UNCONTROLLABLE`
- `servo_target_owner == SERVO_TARGET_OWNER_NONE`
- `control_enabled == 0`

在 `RUN_DIRECT`、`RUN_FEEDBACK`、`CALIBRATION_RUNNING`、`PAUSED` 或 owner 非 NONE 时会拒绝。

### 2.7 事件类 ACK 改成 QUEUED

`CMD_START`、`CMD_STOP`、`CMD_RESET`、`CMD_CALIBRATE`、`CMD_RUN_FEEDBACK`、`CMD_PAUSE` 这类命令收到后只是 post 到状态机事件队列，不能立即代表状态切换成功。

现在这些命令返回：

```c
PROTO_ACK_STATUS_QUEUED = 2
```

含义是“命令已入队，最终状态以 `PACKET_TYPE_SYSTEM_STATUS` 为准”。

仍然保留：

- `PROTO_ACK_STATUS_OK = 0`：立即生效类命令成功，例如部分配置命令。
- `PROTO_ACK_STATUS_UNSUPPORTED_MODE = 1`：当前状态/参数不允许。

### 2.8 删除 AutoCalibration NORMALIZE 死状态

`AUTO_CALIB_STATE_NORMALIZE` 已经不再作为实际路径使用，INIT 阶段直接从当前 abs 开始标定。因此删除：

- `AUTO_CALIB_STATE_NORMALIZE`
- 对应 `case AUTO_CALIB_STATE_NORMALIZE`
- `turnNormalizeTimeoutMs` 参数

这样自动标定状态机更清晰。

## 3. 自动标定失败条件

当前自动标定会在以下条件下失败，并最终触发 `CALIB FAILED`：

1. active scope 没有可标定 joint。
2. 标定 joint 列表非法或重复。
3. 标定过程中状态/owner 被打断，不再满足：
   `CALIBRATION_RUNNING + SERVO_TARGET_OWNER_CALIBRATION + control_enabled == 0`。
4. 初始 encoder、servo abs 或 raw 反馈在等待窗口内缺失。
5. 非当前标定 joint 的 hold target 缺少反馈或无法加入 batch。
6. calibration batch 发布失败。
7. calibration batch 中任一目标电机负载 `>= 800`。
8. 舵机目标超出 `±30719`。
9. tighten/release 过程中丢失 encoder 或 servo 反馈。
10. tighten 点或 release 点搜索失败。
11. 计算出的 encoder span 非法、接近整圈 wrap，或 result build 失败。
12. release 找零时没有足够舵机行程。
13. return zero 超时，或没有满足 abs 误差和回程行程要求。
14. 双拮抗标定中 primary/secondary/encoder 初始反馈缺失。
15. 双拮抗标定中 tight 点寻找失败、目标越界、回 slack 超时。
16. 双拮抗标定结果 span 非法或 result build 失败。
17. 自动标定任务创建失败。

失败后：

- `g_calibrationUIStatus = CALIB_STATUS_FAILED`
- `calibration_fault_latched = 1`
- 状态进入 `UNCONTROLLABLE`
- 需要 `RESET` 才能清除 CALIB fault。

## 4. 当前安全规则总结

### 4.1 RUN 模式准入

`RUN_FEEDBACK`：

- 只能从 `READY` 进入。
- active motor 多圈必须可信。
- active joint 必须在标定工作空间内。
- 由状态机切换 `control_mode = CONTROL_MODE_JOINT`。

`RUN_DIRECT`：

- 可从 `IDLE` 或 `READY` 进入。
- 允许用于多圈 unknown 下的 raw/直控恢复。
- 由状态机切换 `control_mode = CONTROL_MODE_DIRECT_MOTOR`。

### 4.2 fault 清除

| fault | 触发后恢复方式 |
| --- | --- |
| overload | RESET |
| reverse/release guard | RESET |
| calibration failed | RESET |
| system latched fault | RESET |

### 4.3 命令执行结果来源

事件类命令 ACK 只表示 queued。上位机应以 `PACKET_TYPE_SYSTEM_STATUS` 中的 `system_state`、`control_enabled`、`servo_target_owner`、`control_mode` 和 `system_fault_bitmap` 作为最终状态依据。

## 5. 后续维护建议

## 当前代码校正：运行保护和队列清理

当前运行期 overload 阈值以 `ControlTask.cpp` 为准：

```text
RUN_DIRECT:   load >= 600
RUN_FEEDBACK: load >= 600
Latch:        连续 20 个 10ms 控制周期，约 200ms
```

`RUN_FEEDBACK` 增加了 joint command 输入超时：

```text
500ms 内没有新的 joint_command_token，且本地 sine test 未运行
-> 自动 post SYSTEM_EVENT_RUN_FEEDBACK_DONE
```

状态边界的队列清理分为两类：

- `STOP`、`RESET`、fault hold、`CALIBRATE`、calibration failed：清运行时队列和旧 target。
- `START`、`RUN_DIRECT`、`RUN_FEEDBACK`：只清命令/输出队列，不清反馈快照，避免 enable/ready 判定被误伤。

舵机离线/重连时，`ServoCommunicationTask.cpp` 会清旧 target，并在离线后重连时清该舵机旧的 `logicalOffset`、`absoluteReliable`、`initialized`，避免复用上一电源会话的多圈锚点。

1. 以后新增会改变运行状态、owner、control mode、安全边界的命令，应优先做成 `SystemEvent`，由 `StateMachineTask` 统一批准。
2. 通信路由层只负责解析命令和写目标缓存，不应直接改变顶层运行状态。
3. 所有 owner 路径都应覆盖安全保护；现在 `CONTROL` 和 `CALIBRATION` 均包含 overload 保护。
4. 上位机 UI 不应仅凭 ACK 判断命令成功，应等待 system status。
5. 若需要“清 overload 但不 reset 全状态”的能力，建议新增显式 `CMD_CLEAR_FAULT`，不要复用 START。
