# 实机验证与故障排查

最后核对：2026-08-01

## 1. 先分清每一层“在线”的含义

指示灯通常只代表某层最近收到了符合条件的数据，不代表整条链路完全正确：

| 现象 | 最多能证明 | 不能证明 |
| --- | --- | --- |
| ENC 绿色 | P4 最近收到完整、CRC 正确的 S3 磁编批次 | 21 路都有效、某个 Jxx 映射正确、UI 索引正确 |
| ENC 黄色 | 数据在新鲜度/错误状态边界波动，或部分通道失效 | 一定是 CAN 断线 |
| 舵机 online | 该 bus/id 最近同步读成功 | 多圈坐标可信、标定有效、允许输出 |
| ROS2 topic 有 100 Hz | 发布者正常发消息 | desktop 已授权、坐标空间正确、P4 已执行 |
| READY | 当前 active scope 满足工作区和反馈条件 | 任意 scope/任意外部命令都安全 |

排查要沿数据流逐层取证，不要根据一个灯直接换板。

## 2. ENC 绿色但磁编没有读数

常见原因按优先级排列：

1. **UI 看的是 mapped angle，不是 raw。** CAN batch 正常所以 ENC 绿，但 Manual/Auto/URDF CRC 不匹配使 `mapped.validFlags[Jxx]=0`。先看 encoder raw packet `0x0B`。
2. **单路 parity/error flag。** 其他 20 路足以让批次 CRC 正常，问题通道会被 S3 写成 `0xFFFF`；看 S3 `errorFlags/latchedErrors` 和 Jxx raw。
3. **group/mux 映射不匹配。** 138 与 151 板模式、channel map 或手指顺序选错，数据可能出现在另一个 Jxx，而不是完全消失。
4. **active mask/UI 索引过滤。** S3 `ENC_ACTIVE_GROUP_MASK`、P4 active scope 或 desktop 显示筛选没有覆盖该关节。
5. **SPI 接触或模式错误。** MISO/MOSI/SCLK/CS 接触不稳、Mode 1/10 MHz 不匹配、共地或电平问题；可能只影响一个 demux channel。
6. **raw=0 被旧显示逻辑误判。** AS5047P 的零点 0 是合法值，当前 S3 不应把它当断线；若 UI 仍空白，检查 desktop 对 0 和 `0xFFFF/32767` 的区分。
7. **缓存的新鲜度不同。** ENC 总状态基于 CAN batch 时间，而 mapped angle/某个面板使用更严格时间窗，线程卡顿时会出现绿灯但数值暂时空。

最短定位方法：同一时刻记录 S3 21 路 raw → P4 `0x0B` raw/valid → mapped angle valid → desktop model value。第一次发生差异的位置就是故障层。

## 3. RopeInit 或手碰接口时 ENC 偶发黄色

优先考虑以下机制，而不是先认定编码器损坏：

- **供电/地弹噪声。** RopeInit 让舵机周期性收绳，电流阶跃造成 S3/P4/磁编地参考或电源波动，AS5047P parity/error flag 短暂出现；手接触接口也会引入人体静电和耦合。
- **接插件机械扰动。** 手放到磁编与 S3 接口附近会牵动排线、CS/MISO 或公共地，单帧错误后 UI 进入黄色去抖状态。
- **共享 selector 竞争或建立时间不足。** 磁编和触觉有共享选通信号及 mutex；接线串扰、错误 channel 或 selector settle 不足会在触觉 33 ms 访问附近出现偶发错误。
- **CAN/任务抖动。** RopeInit 同时增加 P4 舵机通信与日志，上位机若把接近 timeout 的数据标黄，短暂调度延迟也可能触发；要区分 S3 raw/parity 错误与 P4 batch timeout。
- **标定导致 valid 状态变化。** RopeInit 本身不重新标定，但工作区外/内切换会改变 mapped valid/READY；某些 UI 灯可能把业务有效性与物理 ENC 在线混在一起。

验证方法：示波器同时看 S3 3.3 V、磁编供电、GND bounce 和 SPI MISO/CS；日志记录黄色发生时的 `parity/errorFlags`、CAN CRC/timeout、mapped age、RopeInit motor/load。若手触碰即可复现，先断电检查屏蔽、共地、接插件应力和 ESD 防护，不要带电反复按压接口。

## 4. 上位机指令执行延时

基于任务周期的当前推算为：UpperComm 最多等待约 5 ms，状态机最多 10 ms，Control 最多 10 ms，ServoComm 最多 10 ms；纯软件排队典型约 15~25 ms，保守约 35 ms，再加 UART 和舵机内部执行。它不是实测硬上界。

如果感觉卡顿，分别查看：

- desktop 是否在批量日志/UI 绘图中阻塞发送线程；
- P4 runtime monitor 的任务 max runtime、deadline miss 和 stack watermark；
- ServoComm 同步读 timeout（默认单批 3 ms）及四总线哪一路拖长；
- state event 是否需要一次额外状态迁移；
- 目标队列是否不断被高频新帧覆盖——这是 latest-value 语义，不是丢失后补发；
- 串口协议是否发生错帧重同步。

正式测量要在 desktop send、P4 parse、state accept、control publish、servo driver write 五处用同一 sequence 关联打点，再报告 P50/P95/P99/max。

## 5. 自动标定未找到机械端

检查日志中的 `CHECK_RELEASE`：

- `winAbs < 50`：舵机实际未继续释放，可能目标被安全范围拒绝、owner 丢失或电机没响应；
- `winDeg > 0.75°`：磁编仍在跟随，尚未到端点；
- `angleStable < 2`：停稳未连续确认；
- `releaseDeg < 12°`：总跟随行程不足，不能把起点抖动当端点；
- 达到 8192 counts 仍未成立：触发单腱最大释放保护，应检查方向、绳路和磁编映射；
- span ≥15360 或总行程不在 10°~359°：环形方向/端点结果无效。

不要通过取消 `servoStillReleasing` 或 12° 条件让标定“通过”；这会把电机不动、磁编冻结等故障保存成可信 LUT。

## 6. 通信与 CRC 故障

- 磁编 CRC 错：检查 S3 42-byte 拼包、P4 frame mask、0x106 metadata 和 20 ms 超时；
- 触觉 SPI CRC8 错：检查 Mode 3、1 MHz、selector、response status 和最后一字节 CRC；
- 触觉 CAN CRC16 错：区分传感器侧 CRC8 已失败还是 CAN 分片混批/丢帧；
- 上位机偶发错误但帧仍通过：当前外层 UART 无通用 CRC，应抓原始串口并检查 header/length/type/tail；
- NVS CRC 错：坏槽应被忽略并回退另一槽，不能跳过校验强制加载。

## 7. 标准实机记录

每次问题至少保存：固件/product fingerprint、active scope、system state/owner/fault bitmap、21 路 raw/valid/age、27 路 online/logical ABS/hardware ABS/load、相关 CRC/sequence/timeout、命令 token，以及操作前后时间线。缺这些数据时，“偶尔黄灯”“有延时”“标定卡住”通常无法从代码唯一定位。
