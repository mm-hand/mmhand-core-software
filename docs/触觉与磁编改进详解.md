# 触觉传感器与磁编码器改进详解

> 当前专项文档，最后核对：2026-08-19。磁编当前采用6数据帧 + `0x106` metadata/CRC16、20ms重组；触觉摘要为45 bytes三维力 + 2 bytes模块有效位图 + CRC16、7帧、80ms重组；全量CAN转发默认关闭。本文历史改进过程保留，最终数值以[通信协议与数据校验](通信协议与数据校验.md)为准。

> **对比基线**：`mmhand-cl`（旧版） → `mmhand-main`（当前版本）
>
> 本文档从架构、代码、性能三个维度，逐层解析触觉传感器与磁编码器全链路的改进内容及工程收益。

## 一、架构总览：从"桩代码"到"全链路闭环"

### 1.1 旧版（mmhand-cl）的实际状态

旧版触觉链路在 S3 端仅实现了框架性代码：`HalTactile.cpp` 只有 40 行，`begin()` 函数仅拉高两个 CS 引脚，`update()` 函数内部是模拟数据递增的 mock 逻辑——**从未真正读取过传感器寄存器**。`TactileTask.cpp` 仅 22 行，任务周期 100ms（10Hz），`tactile.update()` 被注释掉，无任何数据输出。

磁编码器方面，旧版可以正常读取 AS5047P 数据并通过 CAN 发送至 P4，但缺乏数据完整性校验（无 CRC），且采样率仅 200Hz。

## 二、S3 端改进详解

### 2.1 HalSensorSpi —— 共享 SPI 总线抽象层（全新模块）

**旧版**：不存在此文件。`HalEncoders.cpp` 内部直接调用 `spi_bus_initialize(SPI2_HOST, ...)` 初始化 SPI 总线，与触觉共享同一 SPI host。

**新版**：新增 `HalSensorSpi.h`（15 行）+ `HalSensorSpi.cpp`（99 行），将 SPI 总线初始化从各驱动中抽出，统一管理：

```cpp
// HalSensorSpi.cpp — 核心初始化逻辑
bool beginSpiDevice(
    spi_host_device_t host, int sckPin, int misoPin, int mosiPin,
    int clockHz, int spiMode, int maxTransferBytes,
    spi_device_handle_t* device, bool* started
) {
    spi_bus_config_t busConfig = {};
    busConfig.mosi_io_num = mosiPin;
    busConfig.miso_io_num = misoPin;
    busConfig.sclk_io_num = sckPin;
    busConfig.max_transfer_sz = maxTransferBytes;
    
    // 自动选择 DMA 通道
    const esp_err_t busErr = spi_bus_initialize(host, &busConfig, SPI_DMA_CH_AUTO);
    // ...
    
    spi_device_interface_config_t devConfig = {};
    devConfig.clock_speed_hz = clockHz;
    devConfig.spics_io_num = -1;  // 软件CS（MUX选择）
    devConfig.queue_size = 1;
    // ...
}
```

**关键改进**：
- **物理分离**：编码器使用 `SPI3_HOST`（GPIO 47/38/9），触觉使用 `SPI2_HOST`（GPIO 21/10/8），消除 SPI 总线竞争
- **`SPI_DMA_CH_AUTO`**：自动分配 DMA 通道，大块触觉数据传输（最大 163 字节）无需 CPU 逐字节搬运
- **`spics_io_num = -1`**：两条总线都使用软件 CS，由外部 MUX GPIO 路由代替硬件片选

**工程收益**：两条 SPI 总线完全独立运行，互不干扰；DMA 释放 CPU 资源，对 500Hz 编码器采样的实时性有直接帮助。

### 2.2 g_sensorSelectMutex —— 共享 MUX 引脚互斥锁

**旧版**：无任何互斥机制。编码器和触觉如果同时操作 MUX 引脚，会产生电气竞争。

**新版**：在 `Config.h` 中声明全局互斥锁，`SystemTasks.cpp` 启动时创建：

```cpp
// Config.h
extern SemaphoreHandle_t g_sensorSelectMutex;

// SystemTasks.cpp — 启动时创建
g_sensorSelectMutex = xSemaphoreCreateMutex();
if (g_sensorSelectMutex == NULL) {
    Serial.println("[FATAL] Sensor selector mutex creation failed!");
    while(1) { vTaskDelay(1000); }
}
```

**编码器侧使用**（`HalEncoders.cpp`）：

```cpp
// transferOnce() — 拿锁 → 切MUX → SPI传输 → 复位MUX → 释放锁
const bool locked =
    (g_sensorSelectMutex == NULL) ||
    (xSemaphoreTake(g_sensorSelectMutex, pdMS_TO_TICKS(20)) == pdTRUE);
if (!locked) return false;

setMux(muxChannel);
// ... SPI transaction ...
setMux(ENC_151_IDLE_CHANNEL);  // 传输完毕后复位到空闲通道

if (g_sensorSelectMutex != NULL)
    xSemaphoreGive(g_sensorSelectMutex);
```

**触觉侧使用**（`HalTactile.cpp`）：

```cpp
// readRegisters() — 覆盖两次SPI事务
xSemaphoreTake(g_sensorSelectMutex, pdMS_TO_TICKS(20));
setAllSelectPinsHigh();        // 全 deselect
setSelectorPattern(pattern);   // 选通目标传感器
spi_device_transmit(cmdTx);    // 发命令帧
spi_device_transmit(respTx);   // 收应答帧
setAllSelectPinsHigh();        // 恢复 deselect
xSemaphoreGive(g_sensorSelectMutex);
```

**工程收益**：编码器在 Core 1（500Hz、优先级 10），触觉在 Core 0（30Hz、优先级 5），双核并行执行。互斥锁保证 GPIO 选择信号不会被打乱，20ms 超时兜底防止死锁。

**核心架构**：

```cpp
// 传感器选择模式表 — 5组×3传感器 = 15个选择模式
constexpr uint8_t makeSelectorPattern(uint8_t group, uint8_t sensorBits) {
    return (uint8_t)((TACTILE_GROUP_CHANNEL_MAP[group] << 2) | (sensorBits & 0x03));

// 两阶段 SPI 读取
bool HalTactile::readRegisters(uint8_t pattern, uint16_t startAddr,
                                uint8_t len, uint8_t* payload, uint8_t& status) {
    // 第一阶段：发送 5 字节命令头
    // [CMD=0xFB] [ADDR_LO] [ADDR_HI] [LEN_LO] [LEN_HI]
    uint8_t cmdTx[] = { 0xFB,
        static_cast<uint8_t>(startAddr & 0xFF),
        static_cast<uint8_t>((startAddr >> 8) & 0xFF),
        len, 0x00 };
    spi_device_transmit(cmdTransaction);

    // 第二阶段：接收 状态字节 + 荷载 + CRC8
    spi_device_transmit(respTransaction);

    // CRC-8 校验
    if (crc8(recvBuf, len + 1) != recvCrc) {
        // CRC 失败，重试一次
        if (retry < kReadRetryCount) goto retry;
        return false;
    }
    return true;
}
```

**数据读取策略**（`update()` 方法）：

```cpp
void HalTactile::update() {
    for (uint8_t g = 0; g < TACTILE_GROUP_NUM; g++) {
        for (uint8_t s = 0; s < TACTILE_SENSOR_PER_GROUP; s++) {
            // 1. 读摘要（地址 1008，15字节：5单元×3轴力）
            bool ok = readSensorSummary(g, s, next);

            // 2. 读分布矩阵（地址 1038，最多156字节：52单元×3轴力）
            bool forcesOk = readSensorForces(g, s, next);

            // 3. 读取失败时保持上次有效数据（零值保持策略）
            if (!forcesOk) {
                // 不清零 forces 数组，保留上一次的值
            }
        }
    }
    // 4. 加锁更新共享数据
    if (xSemaphoreTake(_mutex, pdMS_TO_TICKS(10))) {
        *_data = next;
        xSemaphoreGive(_mutex);
    }
}
```

**关键改进**：

| 改进项 | 旧版 | 新版 | 工程意义 |
|--------|------|------|----------|
| SPI 读取 | 无（mock 数据） | 两阶段寄存器协议 | 真实物理数据 |
| CRC-8 校验 | 无 | 发送端/接收端双重校验 | 抗电磁干扰 |
| 重试机制 | 无 | 1 次重试 + 2ms 间隔 | 提高读取成功率 |
| 零值保持 | 无 | 读取失败时保持上次数据 | 避免控制环路跳变 |
| 诊断计数器 | 无 | `TactileReadDiag` 结构体 | 运行时故障定位 |
| 数据互斥锁 | 无 | `_mutex` 保护 `TactileData` | 多任务安全访问 |
| Boot 引脚预处理 | 无 | `prepareBootSelectPins()` | 防止启动时 MUX 误选通 |

### 2.4 TactileTask —— 从空壳到 30Hz 全量处理管线

**旧版**（22 行）：

```cpp
void Task_Tactile(void*) {
    for (;;) {
        // tactile.update();  // 被注释掉
        vTaskDelay(pdMS_TO_TICKS(100));  // 10Hz
    }
}
```

**新版**（239 行）：实现了完整的数据处理管线。

**核心架构**：

```cpp
void Task_Tactile(void*) {
    constexpr uint32_t kTactileTaskPeriodMs = 33;  // ~30Hz

    for (;;) {
        TickType_t xLastWake = xTaskGetTickCount();

        // 1. SPI 全量扫描（15 个传感器）
        tactile.update();

        // 2. 获取数据快照（加锁）
        TactileData data;
        tactile.getData(data);

        // 3. CAN 中继（可选）
        #if ENABLE_TACTILE_CAN_RELAY
        const uint8_t tactileSeq = twaiBus.sendTactileSummary(data);
        #else
        const uint8_t tactileSeq = tactileSeqCounter++;
        #endif

        // 4. 串口摘要包（0x0A 类型）
        sendSerialTactileSummary(data, tactileSeq);

        // 5. 串口全量转储包（0x0E 类型，分片）
        if ((tactileSeq % kFullDumpDecimation) == 0) {
            sendSerialTactileFullDump(data, tactileSeq);
        }

        // 6. 周期调试打印
        vTaskDelayUntil(&xLastWake, pdMS_TO_TICKS(kTactileTaskPeriodMs));
    }
}
```

**串口数据包序列化**：

```cpp
// 摘要包（0x0A）— 每周期发送
void sendSerialTactileSummary(const TactileData& data, uint8_t seq) {
    uint8_t flat[TACTILE_SUMMARY_BYTES];
    flattenTactileSummary(data, flat);         // 结构体 → 平坦字节
    writeFilteredSummaryAxes(flat);            // 噪声门限滤波

    // 帧格式：[0xFE][len][0x0A][seq][payload...][0xFF]
    Serial.write(0xFE);
    Serial.write(static_cast<uint8_t>(1 + 1 + TACTILE_SUMMARY_BYTES));
    Serial.write(0x0A);  // PACKET_TYPE_TACTILE
    Serial.write(seq);
    Serial.write(flat, TACTILE_SUMMARY_BYTES);
    Serial.write(0xFF);
}

// 全量转储包（0x0E）— 分片发送
void sendSerialTactileFullDump(const TactileData& data, uint8_t summarySeq) {
    uint8_t flat[TACTILE_FULL_BYTES];
    flattenTactileFull(data, flat);

    // 分片：每片 240 字节，含魔数 "T2" + 片头 + CRC-16
    for (size_t offset = 0; offset < TACTILE_FULL_BYTES; offset += chunkPayload) {
        // [0xFE][len][0x0E]["T2"][summarySeq][fragIdx][fragTotal]
        //        [crc16_lo][crc16_hi][chunk_data...][0xFF]
    }
}
```

**噪声门限滤波**（`writeFilteredSummaryAxes`）：

```cpp
void writeFilteredSummaryAxes(uint8_t* flat) {
    for (size_t i = 0; i < TACTILE_SUMMARY_BYTES; i += 3) {
        // 如果三个轴的绝对值都低于噪声门限，整体归零
        if (axisMagnitude(flat[i]) <= TACTILE_SUMMARY_NOISE_FLOOR &&
            axisMagnitude(flat[i+1]) <= TACTILE_SUMMARY_NOISE_FLOOR &&
            flat[i+2] <= TACTILE_SUMMARY_NOISE_FLOOR) {
            flat[i] = 0; flat[i+1] = 0; flat[i+2] = 0;
        }
    }
}
```

#### 2.5.2 CAN 发送率提升：100Hz → 250Hz


**收益**：P4 端每 4ms 收到一批最新角度，对 1kHz 内环控制提供更密集的反馈。

#### 2.5.3 CAN 编码器帧加入 CRC-16 校验

**旧版**：6 帧数据（`0x100`~`0x105`），最后一帧的剩余字节填零，无完整性校验。P4 收到 `0x105` 即认为数据完整。

**新版**：数据帧数量动态计算 + 新增 CRC 元数据帧：

```cpp
// HalTWAI.cpp — sendEncoderData()
uint8_t HalTWAI::sendEncoderData(const EncoderData& encData) {
    constexpr uint8_t frameCount = CAN_ENC_FRAME_COUNT;  // (21+3)/4 = 6

    // 1. 发送数据帧
    for (uint8_t i = 0; i < frameCount; i++) {
        // ... 每帧 4 个 uint16_t 角度值
    }

    // 2. 计算 CRC-16-CCITT
    uint16_t crc = crc16Ccitt(payload, CAN_ENC_PAYLOAD_BYTES);

    // 3. 发送 CRC 元数据帧（CAN_ID_ENC_CRC = 0x106）
    uint8_t crcFrame[8] = {
        seq,                        // 滚动序号
        static_cast<uint8_t>(crc >> 8),   // CRC 高字节
        static_cast<uint8_t>(crc & 0xFF), // CRC 低字节
        frameCount,                 // 数据帧数量
        static_cast<uint8_t>(CAN_ENC_PAYLOAD_BYTES), // 荷载字节数
        0, 0, 0
    };
    sendFrame(CAN_ID_ENC_CRC, crcFrame, CAN_ENC_CRC_DLC);

    return frameCount + 1;  // 返回总发送帧数
}
```

**P4 端重组验证**（`CanCommTask.cpp`）：

```cpp
// P4 收到 CRC 帧后验证
if (rxMsg.identifier == CAN_ID_ENC_CRC) {
    uint16_t recvCrc = (state.buffer[crcOff] << 8) | state.buffer[crcOff+1];
    uint16_t calcCrc = crc16Ccitt(encoderPayload, CAN_ENC_PAYLOAD_BYTES);

    if (recvCrc != calcCrc) {
        // CRC 不匹配，丢弃整批数据
        resetEncoderReassembly(&state);
        return;
    }
    // CRC 匹配，发布有效数据
    xQueueOverwrite(sharedData->canRxQueue, &rxBuffer);
}
```

**收益**：CAN 总线在电磁干扰下可能出现的位翻转或丢帧，现在可以被 P4 端 100% 检测到。旧版在丢帧时会将错位的编码器值送入控制环路，新版彻底消除了这种隐患。

#### 2.5.4 MUX 空闲通道复位


## 三、CAN 协议改进详解

### 3.1 编码器 CAN 帧对比

**旧版协议**：

```
CAN ID 0x100~0x105: 6帧纯数据，每帧 8 字节
  - 0x100: [Enc0_Hi Enc0_Lo Enc1_Hi Enc1_Lo Enc2_Hi Enc2_Lo Enc3_Hi Enc3_Lo]
  - ...
  - 0x105: [Enc20_Hi Enc20_Lo 0x00 0x00 0x00 0x00 0x00 0x00]
  
P4 重组逻辑: 收到 0x105 即认为完整 → 发布
```

**新版协议**：

```
CAN ID 0x100~0x105: 6帧数据（同旧版布局）
CAN ID 0x106:       CRC 元数据帧（新增）
  - [seq][CRC_Hi][CRC_Lo][frameCount][payloadBytes][0x00][0x00][0x00]

P4 重组逻辑: 收到 0x106 → 用 frameMask 检查是否集齐 → CRC-16 校验 → 发布
超时保护: 20ms 内未集齐则丢弃
```

### 3.2 触觉 CAN 帧（全新协议）

**触觉摘要帧**（CAN ID `0x240`~`0x246`，共 7 帧）：

```
每帧 8 字节:
  Byte 0:  seq（滚动序号，0~255 循环）
  Byte 1~7: 触觉摘要荷载（45字节力 + 2字节有效位图 + 2字节CRC）

bit0~bit14依次表示G0S0~G4S2本轮摘要SPI及CRC8有效；CRC-16覆盖力数据和有效位图。

P4 重组: frameMask 集齐检查 + CRC-16 校验
超时保护: 80ms
```

**触觉全量转储帧**（CAN ID `0x400` 起，帧数动态计算）：

```
每帧 8 字节:
  Byte 0:  seq
  Byte 1~7: taxel 分布数据（每帧 7 字节有效荷载）

P4 重组: 位图数组跟踪数百帧 + CRC 校验
超时保护: 400ms
```

### 3.3 CAN TX 队列扩容

```cpp

// 新版

```

**当前解释**：摘要周期产生 7 帧，编码器批次 7 帧（6 数据 + 1 metadata/CRC）；全量数据为 1530 bytes，约 219 个 7-byte 分片，不能归入“14~50 帧”预算。CAN 全量转储默认关闭，512 深度队列只是缓冲手段，不能替代 bus-load/deadline 测量。

### 5.1 新增 TactileSerialComm —— 独立触觉串口通道

**旧版**：不存在此类。触觉数据仅通过 P4 主串口间接获取。

**新版**（`comm_layer.py`，约 250 行）：独立连接 S3 USB 串口，直接接收触觉原始数据流：

```python
class TactileSerialComm:
    """独立触觉串口通道 — 直连 S3 获取原始触觉数据"""

    def __init__(self, port):
        self._serial = serial.Serial(port, BAUDRATE, timeout=SERIAL_TIMEOUT)
        self._rx_queue = queue.Queue(maxsize=RX_QUEUE_MAXSIZE)
        self._rx_thread = threading.Thread(target=self._rx_loop, daemon=True)

    def _rx_loop(self):
        while self._running:
            if self._serial.in_waiting:
                data = self._serial.read(self._serial.in_waiting)
                self._process_packets(data)  # 解析 0x0A 摘要 + 0x0E 全量
            else:
                time.sleep(RX_POLL_SLEEP)
```

## 七、带宽评估

### 7.1 CAN 总线带宽占用

```
编码器: 7帧 × 108bit × 250Hz = 189,000 bps ≈ 189 kbps
触觉摘要: 7帧 × 108bit × 30Hz = 22,680 bps ≈ 23 kbps
错误详情(偶发): ~3帧 × 108bit × 1Hz ≈ 324 bps

总计峰值: ~212 kbps (占 1Mbps 的 21.2%)
```

**结论（摘要开启、全量关闭）**：编码器与触觉摘要的估算负载可控，但还要计入 stuff bit、仲裁、ACK、错误重发和其他帧。旧版“固定 21%”只能作为理想线速估算，最终以 TWAI bus-load 和 deadline miss 实测为准。

### 7.2 串口带宽

```
S3 → 桌面 (921600 baud):
  当前全量 payload: 1530 bytes/批
  若按 30Hz 连续发送，仅 payload 已达 45,900 B/s
  还需计入串口 8N1、协议字段和可能的重发，不能沿用旧版固定 18% 结论
```

## 八、关键设计决策解析

### 8.1 为什么触觉全量转储默认走串口而非 CAN？

触觉全量转储当前为 1530 bytes，一批约需 219 个 7-byte CAN 分片；若以 30 Hz 连续发送，Classic CAN 1 Mbit/s 无法仅凭 payload 位数宣称安全，还会严重挤压磁编批次。因此 `ENABLE_TACTILE_CAN_FULL_DUMP` 默认关闭，全量主要走 S3 串口；如需开启必须降低频率并实测 CAN 队列、bus load、磁编 CRC/timeout 和 P4 runtime。

### 8.2 为什么 SPI 时钟从 5MHz 降到 1MHz？

旧版 `SPI_FREQ_TAC = 5000000`（5MHz），新版降至 `1000000`（1MHz）。这是因为新版实现了完整的两阶段寄存器读取协议（命令帧 + 应答帧），在 5MHz 下 CRC-8 错误率显著上升，1MHz 在 15 个传感器 × 2 次 SPI 事务 = 30 次传输/周期的负载下，仍能在 33ms 内完成全量扫描。

### 8.3 为什么编码器 CAN 帧从 6 帧变成 7 帧？

新增的第 7 帧（`0x106`）是 CRC 元数据帧，包含滚动序号 `seq`、CRC-16 校验值、帧数和荷载字节数。P4 端先累积 6 帧数据，收到 CRC 帧后用 `frameMask` 确认完整性，再校验 CRC-16。这种设计让 P4 可以区分"正常接收"和"丢帧后的错位拼装"，是保证关节控制安全性的关键改进。
