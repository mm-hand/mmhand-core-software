# 通信协议与数据校验

最后核对：2026-08-01

## 1. 三条通信链路

| 链路 | 物理层/速率 | 作用 | 完整性机制 |
| --- | --- | --- | --- |
| desktop ↔ P4 | USB UART，921600 bps | 命令、状态、调试、标定和传感上报 | 帧头/类型/定长 payload/帧尾 + 业务校验；外层帧当前无通用 CRC/sequence |
| S3 ↔ P4 | Classic CAN，1 Mbit/s | 21 路磁编、错误详情、触觉摘要/全量 | CAN 控制器自带帧 CRC；应用层分批 sequence/CRC16/超时重组 |
| P4 ↔ 舵机 | 4 路 UART，1 Mbit/s | 27 路飞特舵机同步读写 | 飞特协议 checksum，由 driver/SDK 处理 |

完整性必须分层描述。CAN 的硬件 CRC 只能保护单个 CAN frame，不能证明拆成 6~219 帧的应用批次属于同一次采样；所以 S3/P4 又增加应用层 CRC16。上位机串口外层帧则尚未提供同等级的通用 CRC，不能写成“所有协议均带 CRC”。

## 2. 上位机串口协议

协议单一事实源是 `desktop/resources/config/upper_protocol_schema.json`，由 `tools/generate_upper_protocol.py` 生成：

- P4：`src/generated/UpperProtocol.generated.h`
- desktop：`desktop/core/generated_upper_protocol.py`

禁止分别手改 C++ 和 Python 常量。当前接收 buffer 为 512 bytes；大部分 P4 上行包带 4-byte timestamp。帧以 `0xFE` 开始、`0xFF` 结束，并按 packet type 对应的固定 payload 长度解析。

### 2.2 P4 → desktop 上报

当前 packet type：sensor `0x01`、calibration ack `0x02`、servo angle `0x03`、joint debug `0x04`、telemetry `0x05`、protocol ack `0x06`、fault `0x07`、servo raw `0x09`、tactile `0x0A`、encoder raw `0x0B`、system `0x0C`、ABS limit `0x0D`、calibration snapshot `0x0E`、tactile full `0x0F`、calibration diag `0x10`、task diag `0x11`、manual reference `0x12`、logical range `0x13`、product fingerprint `0x14`。

周期性上报节流来自 schema：fault 200 ms、system 100 ms、task diag 250 ms、ABS limit 500 ms、logical range 500 ms、calibration snapshot 1000 ms、manual reference 1000 ms、product fingerprint 2000 ms。

字段字节序不是“全协议统一”：关节角 float 为 little-endian；多数字段编码 helper 和 int16/int32 命令按各自 codec 使用 big-endian。新增字段时必须查 schema 和具体 encode/decode 函数，不能凭相邻包猜测。

### 2.3 为什么当前外层帧仍有风险

帧头、定长和帧尾能找回边界，也能拒绝明显截断，但不能可靠发现 payload 中恰好翻转且长度仍正确的 bit。产品指纹、标定快照等内部数据可以有独立 CRC，不等于整条串口帧受保护。

若后续升级，推荐在 schema 中统一增加 `version + sequence + payload CRC16/CRC32`，并设计旧版兼容窗口；不能只在 P4 末尾临时多发两个字节，否则旧 desktop 会失帧同步。

## 3. S3 → P4 CAN 分帧

### 3.1 磁编批次

21 路 raw 共 42 bytes，S3 使用 ID `0x100~0x105` 发送 6 个数据帧，再用 `0x106` 发送 metadata：sequence、CRC16、frame count=6、payload bytes=42 等。P4 维护 frame mask，收齐数据和 metadata 后对 42 bytes 重新计算 CRC16；20 ms 内未完成则丢弃整批。

注意：数据帧 `0x100~0x105` 本身没有逐帧 sequence，当前 sequence 主要出现在 metadata。frame mask + 20 ms 窗口 + CRC16 能高概率拒绝混批，但不是严格的逐帧代次绑定。若需要形式上消除混批可能，应在每个数据帧携带 sequence，代价是每帧少 1 byte 有效数据。

### 3.2 触觉与错误详情

- 错误详情：ID `0x1F0~0x1F2`，3 帧，重组超时 100 ms；300 ms 未有完整批次会清空旧错误表。
- 触觉摘要：ID `0x240~0x246`，45 bytes 数据 + 2 bytes CRC16，每帧含 sequence，重组超时 80 ms。
- 全量触觉：从 `0x400` 起分片，共 1530 bytes，重组超时 400 ms；CAN full dump 默认关闭，避免大量分片挤占磁编实时流量。

S3 编码器任务每 2 ms 更新 latest queue，CAN 任务每 4 ms 取最新快照发送；触觉任务周期 33 ms。队列深度 1 是有意设计：实时控制需要最新样本，积压一串过期磁编帧比丢掉中间采样更危险。

## 4. 当前所有校验算法

| 位置/数据 | 算法 | 实现方式 | 说明 |
| --- | --- | --- | --- |
| AS5047P SPI word | 芯片协议奇偶校验 + error flag | 逐 word parity 计算 | 不是 CRC；检查磁编返回字完整性 |
| 触觉芯片 SPI | CRC8，init `0xFF` | 256 项查表法 `kCrc8Table` | 每次寄存器响应都比较 recv/calc CRC |
| S3↔P4 磁编/触觉批次 | CRC16-CCITT，poly `0x1021`，init `0xFFFF` | 逐字节、逐 bit 移项 | 应用层批次校验，不是 ESP 硬件 CRC |
| P4 协议/标定块 helper | CRC16-CCITT，poly `0x1021`，init `0xFFFF` | 逐 bit 移项 | 用于特定快照/块语义，不覆盖所有上位机外层帧 |
| Manual 标定 NVS | CRC32，reflected poly `0xEDB88320` | 逐 bit 移项 | 结构 CRC + 端点语义 reference CRC |
| 多圈 NVS | CRC32，reflected poly `0xEDB88320` | 逐 bit 移项 | 快照 CRC，并复用于 HardwareMap signature |
| Classic CAN 单帧 | CAN 标准 CRC | TWAI 控制器硬件完成 | 与应用层 CRC16 作用不同 |
| 飞特串口帧 | 协议 checksum | SDK/driver | 由舵机协议实现，不是本项目 CRC helper |

### 4.1 查表法与逐位法怎么选

查表法适合高频、大数据量且 Flash/只读内存足够的场景：每个 byte 一次索引，速度稳定，但要占用表空间，并要保证表的 polynomial/reflection/init 与对端完全一致。触觉每 33 ms 要读取多组、最多 1530 bytes 数据，CRC8 表只有 256 bytes 左右，换取吞吐是合理的。

逐位移项法适合短 payload、低频持久化或代码尺寸/可审计性优先的场景：不需要表，几行代码可直接对应多项式，但每 byte 要循环 8 次。磁编仅 42 bytes、触觉摘要 45 bytes，CAN 发送频率虽高但该计算量对 S3/P4 很小；NVS 写入更是低频。因此当前 CRC16/CRC32 使用逐位法是合理选择，并非遗漏硬件加速。

若开启 CAN 全量触觉高频转发，1530 bytes × 逐位 CRC16 的成本会显著增加，应以 CPU runtime profile 决定是否改为表驱动或 ESP ROM/硬件加速。优化前先建立测试向量，确保两端结果一致，不能只替换一侧。

## 5. 上位机命令到舵机的时延

当前没有一项实机端到端统计可以宣称“固定延时”。按调度周期估算一帧关节角命令：

```text
串口传输/解析
  → 最多约 5 ms 等待 UpperComm
  → 最多约 10 ms 等待状态准入/owner 更新（需要状态事件时）
  → 最多约 10 ms 等待 Control 生成目标
  → 最多约 10 ms 等待 ServoComm 执行
  → UART 发送与舵机内部响应
```

任务相位随机时，纯软件排队典型约 15~25 ms，保守调度上界约 35 ms，再加串口传输、同步读阻塞和舵机自身执行延时。重复的 RUN_FEEDBACK 连续目标可能不需要每帧重新走完整状态迁移，所以实际分布会不同。这是基于周期的推算，不是测量结论。

要得到可写进测试报告的数字，应在 desktop 发送处写入 sequence/timestamp，在 P4 收帧、Control 出目标、ServoComm 调用 driver 后分别打点；最好再用逻辑分析仪测 USB-UART TX 到舵机总线 TX 的边沿。报告 P50/P95/P99 和最大值，而不是只测一帧。

## 6. 协议修改检查清单

1. 先改 JSON schema，再运行生成器；
2. 同时检查 payload 长度、buffer 上限、字节序、disconnect sentinel 和 timestamp；
3. 多帧数据必须定义 sequence、frame count、完整批次 CRC、重组超时和重复帧策略；
4. 新命令必须经过状态准入和 owner，不能在 parser 中直接写舵机；
5. 用已知测试向量覆盖 CRC、截断、错长度、乱序、重复、超时和未知 packet type；
6. 运行 `python tools/generate_upper_protocol.py --check`，确认生成物未漂移。
