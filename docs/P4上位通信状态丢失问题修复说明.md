# P4 上位通信状态丢失问题修复说明

## 1. 文档目的

本文记录一次 P4 下位机与 Windows 上位机之间的状态通信故障，包括：

- 故障现象和正确预期；
- 为什么按 P4 RESET 后只能短暂恢复；
- P4 FreeRTOS 任务调度和上位机状态判定中原有的问题；
- 本次代码修复；
- 后续排查和回归测试方法。

修复日期：2026-06-29。

## 2. 故障现象

测试条件为：

- P4 已通过 USB 串口连接 Windows 上位机；
- 舵机、S3/CAN、磁编码器等外设均未连接；
- 上位机串口指示灯为绿色；
- 顶部状态栏显示 `SYS -`、`CALIB IDLE`、`OL OK`、`TURN -`；
- 终端出现：

```text
Protocol warning: no stream-mode ACK from firmware; continue with current decoding.
```

按下 P4 单片机 RESET 后，上位机能够短暂收到状态和故障，几秒后又重新失去二进制状态数据。

## 3. 正确行为

串口打开并不代表系统健康。外设全部未连接时，P4 应保持上报系统状态，并明确报告不可控和离线故障。

正常情况下应满足：

1. `SYSTEM_STATUS` 每 100 ms 上报一次；
2. `FAULT_STATUS` 每 200 ms 上报一次；
3. 系统状态为 `UNCONTROLLABLE`；
4. 故障至少包含 CAN/磁编码器离线、舵机离线和多圈位置未知；
5. 上位机显示红色系统故障，而不是 `SYS -` 或绿色健康状态。

日志中 RESET 后曾收到故障位图 `0x51`：

```text
0x51 = 0x01 | 0x10 | 0x40
     = CAN_OFFLINE | SERVO_OFFLINE | MULTITURN_UNKNOWN
```

这说明 P4 状态机对“外设未连接”的故障判断本身是正确的，异常发生在状态上报链路。

## 4. 日志证据

故障日志位于：

```text
desktop/logs/session_20260629_134210.log
```

关键时间线如下：

```text
13:45:08  no stream-mode ACK from firmware
13:45:09  lower status/servo feedback sync timed out
13:45:26  RX diag total=0.0 pkt/s，只有固件文本输出
13:45:42  用户按下 P4 RESET，出现 <<<SYS_READY>>>
13:45:42  收到 0x51 系统故障，上位机执行故障停机
13:45:46  RX diag total=32.0 pkt/s，二进制协议短暂恢复
13:46:06  RX diag 再次变成 0.0 pkt/s
```

在二进制协议停止后，P4 仍持续输出：

```text
[STATE] servo offline activeMask=... missing=...
```

由此可以判断：

- USB 串口没有物理断开；
- P4 状态机仍在运行；
- 停止推进的是 P4 `upperCommunicationTask` 或其获得 CPU/发送机会的路径；
- 重新连接 PC 串口无法恢复该 FreeRTOS 任务；
- RESET 会重新创建任务，所以能够短暂恢复。

## 5. 根因分析

### 5.1 P4 舵机通信任务可能长期占用 CPU

原任务优先级如下：

```text
ControlTask              priority 4
ServoCommunicationTask  priority 3
CanCommunicationTask    priority 3
StateMachineTask         priority 2
UpperCommunicationTask  priority 1
```

`ServoCommunicationTask` 设计周期为 10 ms，原循环末尾使用：

```cpp
vTaskDelayUntil(&lastWakeTime, taskPeriodTicks);
```

外设全部断开时，舵机总线需要进行同步读取、超时等待和离线探测。一轮处理可能超过 10 ms。

当任务已经超过目标唤醒时间时，`vTaskDelayUntil` 会立即返回，不会真正进入阻塞状态。由于舵机任务优先级为 3，而上位通信任务优先级只有 1，连续超周期可能使上位通信任务长时间得不到执行机会。

结果是：

- 状态机仍可能得到少量运行机会并打印文本；
- `upperCommunicationTask` 无法按 5 ms 周期推进；
- `SYSTEM_STATUS`、`FAULT_STATUS` 和命令 ACK 停止发送；
- PC 串口仍保持打开，但协议已经不在线。

### 5.2 Joint debug 队列原来采用无上限清空

上位通信任务原来使用 `while` 持续清空 `jointDebugQueue`：

```cpp
while (xQueueReceive(jointDebugQueue, &debugData, 0) == pdTRUE) {
    sendDataPacket(...);
}
```

如果高优先级控制任务持续生产 debug 数据，上位通信任务可能在一轮循环中花费过多时间发送 debug 包，推迟后面的系统状态、过载状态和其他心跳包。

这不是串口完全停止的唯一原因，但会扩大任务调度和串口拥塞问题。

### 5.3 Stream mode 协商只在打开串口时发送一次

上位机原来在打开串口后立即发送一次 `CMD_SENSOR_STREAM_MODE`。

如果 P4 随后才 RESET，或者 USB 串口打开过程触发了板卡重启，这一帧会在固件任务准备完成前丢失。P4 启动完成后上位机不会重新协商，因此出现：

```text
no stream-mode ACK from firmware
```

### 5.4 上位机把“串口打开”误认为“通信健康”

原绿色圆点只检查串口对象是否处于打开状态，没有检查是否持续收到 `SYSTEM_STATUS`。

因此以下两种情况使用了相同的绿色显示：

- 串口已打开且 P4 协议正常；
- 串口已打开但 P4 二进制协议任务已经停止。

### 5.5 状态数据没有独立时效性

原 `HandModel` 只有 `has_system_status_data`，没有记录最后一次系统状态包的接收时间。

一旦收过状态，该状态可以永久保留；即使 P4 后续停止上报，上位机也无法判断它已经 stale。

此外，部分命令 ACK 会设置 `has_system_status_data = True`。但 ACK 只包含命令、应用模式和结果，并不包含完整的故障位图、在线位图和多圈状态，因此不能证明系统状态有效。

### 5.6 “没有过载数据”被显示为“没有过载”

`servo_overload_fault` 默认值全部为 `False`。原 UI 看到没有置位项就显示 `OL OK`，但没有区分：

- 已收到 `FAULT_STATUS`，位图确实为 0；
- 从未收到 `FAULT_STATUS`，真实过载状态未知。

这是典型的把 unknown 错误解释为 healthy。

## 6. 修复内容

### 6.1 舵机任务超周期时强制让出 CPU

文件：

```text
ESP32-P4/ServoBoardMain/src/communication/servo/ServoCommunicationTask.cpp
```

修复后会在调用 `vTaskDelayUntil` 前判断本周期是否已经超时。如果已经超周期，则额外阻塞 1 tick：

```cpp
const TickType_t nextWakeTime = lastWakeTime + taskPeriodTicks;
const bool periodOverrun = (int32_t)(xTaskGetTickCount() - nextWakeTime) >= 0;
vTaskDelayUntil(&lastWakeTime, taskPeriodTicks);
if (periodOverrun) {
    vTaskDelay(1);
}
```

这样即使大量舵机离线导致扫描超时，也会为状态机和上位通信任务留出运行窗口。

### 6.2 限制每轮 joint debug 发送数量

文件：

```text
ESP32-P4/ServoBoardMain/src/communication/upper/UpperCommTask.cpp
```

每轮最多发送 4 个 joint debug 包，剩余数据留到后续循环处理。这样系统状态和故障心跳不会被 debug 队列长期推迟。

### 6.3 P4 启动完成后重新协商 stream mode

文件：

```text
desktop/core/comm_layer.py
```

上位机检测到固件输出：

```text
<<<SYS_READY>>>
```

后，会重新发送 `CMD_SENSOR_STREAM_MODE`，避免首次命令在 P4 RESET 或启动期间丢失。

### 6.4 为系统状态和过载状态增加接收时间

文件：

```text
desktop/core/data_models.py
desktop/core/comm_layer.py
```

新增：

```text
system_status_last_rx_ts
has_fault_status_data
fault_status_last_rx_ts
```

只有真正解析到 `PACKET_TYPE_SYSTEM_STATUS` 时，才更新系统状态有效标记和时间戳。普通命令 ACK 不再冒充完整系统状态。

### 6.5 UI 改为 fail-closed 显示

文件：

```text
desktop/ui/ui_app.py
```

状态显示规则调整为：

| 条件 | SYS 显示 | 颜色 |
| --- | --- | --- |
| 串口未连接 | `SYS -` | 中性 |
| 串口已打开但从未收到状态 | `SYS COMM FAULT` | 红色 |
| 超过 1 秒未收到状态心跳 | `SYS STATUS LOST` | 红色 |
| 状态新鲜且存在故障位 | 具体故障或 `SYS FAULT xN` | 红色 |
| 状态新鲜且无故障 | 当前系统状态 | 绿色 |

过载显示调整为：

| 条件 | OL 显示 |
| --- | --- |
| 未连接 | `OL -` |
| 从未收到过载状态 | `OL NO DATA` |
| 过载状态超过 1 秒未更新 | `OL STALE` |
| 已收到状态且位图为 0 | `OL OK` |
| 存在过载 | 显示电机编号和触发负载 |

串口指示灯现在区分：

- 绿色：串口已打开，且 `SYSTEM_STATUS` 心跳正常；
- 橙色：串口已打开，但协议状态缺失或 stale；
- 红色：串口未连接。

### 6.6 RUN 状态依赖新鲜系统心跳

文件：

```text
desktop/core/core_logic.py
```

`is_started()` 不再只返回历史 `_started`。只有最后一次 `SYSTEM_STATUS` 在 1 秒以内时，系统才允许继续显示 RUN。

这可以防止通信已经失活，但上位机仍保留旧 RUN 状态。

## 7. 修复后的完整状态链

```text
外设离线
  -> P4 舵机/CAN检测到离线
  -> StateMachineTask 生成 fault bitmap
  -> UpperCommunicationTask 周期发送 SYSTEM_STATUS/FAULT_STATUS
  -> desktop 记录独立接收时间
  -> UI 显示 CAN/SERVO/MULTITURN 故障
```

如果 P4 上位通信停止：

```text
SYSTEM_STATUS 超过 1 秒未更新
  -> SYS STATUS LOST
  -> 串口灯由绿色变为橙色
  -> RUN 判定失效
  -> OL 不再显示虚假的 OK
```

## 8. 回归测试

### 8.1 外设全部断开

1. 烧录修复后的 P4 固件；
2. 不连接舵机、S3/CAN和磁编码器；
3. 打开上位机并连接 P4；
4. 持续观察至少 60 秒。

预期：

- 不出现持续性的 stream-mode ACK warning；
- `RX diag` 持续大于 0，不会在几秒后降为永久 0；
- SYS 显示 CAN、SERVO、MULTITURN 等故障；
- 系统保持 STOP/UNCONTROLLABLE；
- 不显示虚假的 `OL OK`，除非已收到有效 `FAULT_STATUS`。

### 8.2 P4 运行期间按 RESET

预期：

- RESET 期间短暂显示 `SYS STATUS LOST` 或 `SYS COMM FAULT`；
- 收到 `<<<SYS_READY>>>` 后自动重新协商 stream mode；
- 状态心跳自动恢复，不需要重启上位机。

### 8.3 模拟状态心跳中断

预期：

- 1 秒内由正常状态切换为 `SYS STATUS LOST`；
- 串口灯变为橙色；
- RUN 显示和控制有效状态被撤销；
- 恢复状态包后自动回到真实系统状态。

### 8.4 正常连接全部外设

预期：

- 只有在系统状态包新鲜、故障位图为 0 时显示健康；
- 舵机/CAN热插拔后在线位图和系统故障能实时更新；
- 状态诊断不会影响控制周期和舵机反馈。

## 9. 经验总结

本次问题不是单一的 UI 显示错误，而是下位机任务调度和上位机状态语义共同造成的：

1. 物理串口在线不等于协议在线；
2. 协议在线不等于外设健康；
3. 所有健康状态都必须有独立的有效标记和更新时间；
4. unknown 不能显示为 OK；
5. 高频 debug/遥测必须限流，不能阻塞安全状态心跳；
6. 周期任务超时时必须确保低优先级安全通信仍能获得 CPU；
7. RESET/重连后的协议协商必须支持重新执行。

后续新增状态字段时，应同时定义数据来源、更新频率、stale 阈值、断开显示和恢复条件，避免再次出现“串口看起来在线，但系统状态实际上已经失效”的问题。
